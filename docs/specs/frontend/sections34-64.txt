==================================================
34. DEFINITION OF SUCCESS
==================================================

The frontend succeeds when:

1. The backend returns candidate geographic regions.

2. The frontend automatically plots those regions in their real
   geographic positions.

3. The user can zoom from the United States into a candidate region.

4. Candidate regions use actual GeoJSON geometry from the backend,
   not manually drawn shapes.

5. Ranked candidates display map markers such as:

   #1
   #2
   #3

6. Clicking either a marker, polygon, or result-list item selects
   the same candidate.

7. Selecting a candidate displays:

   - overall score;
   - six challenge-factor scores;
   - raw physical measurements;
   - screening status;
   - Pareto status;
   - uncertainty;
   - missing information;
   - verification requirements;
   - source provenance.

8. The user can enable and disable geographic layers.

9. The user can change the data-center configuration and execute:

   FIND LOCATIONS

10. The frontend sends that configuration to the actual backend
    instead of calculating the ranking itself.

11. New backend results replace the old candidate visualization.

12. Loading, error, partial-data, and zero-candidate states work.

13. The interface works on desktop and mobile.

14. The frontend remains usable with thousands of grid cells.

15. UNKNOWN values remain visibly unknown.

16. The UI never implies that a candidate region is a verified
    construction parcel.

17. The UI never invents geographic or model values.

18. Mock data are clearly identified as DEMO DATA.

19. A user can compare up to three candidate regions.

20. Source information is accessible for important metrics.

21. The application can visualize current and future scenarios when
    those scenarios are actually returned by the backend.

22. The application can run without the optional globe mode.

23. The main U.S. map remains the primary functional interface.

35. BACKEND INTEGRATION
==================================================

Do NOT tightly couple map components to one API response.

Create an API/data transformation layer:

Backend Response
       ↓
API Adapter
       ↓
Frontend Domain Model
       ↓
Map + UI Components

For example:

backend:
snake_case

frontend:
camelCase

Conversion should happen in the API adapter.

Create TypeScript domain types similar to:

type CandidateRegion = {
    id: string;
    rank: number | null;
    overallScore: number | null;

    centroid: {
        latitude: number;
        longitude: number;
    };

    geometry: GeoJSON.Geometry;

    screeningStatus:
        | "PASS"
        | "FAIL"
        | "CONDITIONAL"
        | "UNKNOWN";

    paretoOptimal: boolean | null;

    factorScores: {
        powerCarbon?: number;
        water?: number;
        land?: number;
        climate?: number;
        heatReuse?: number;
        communityEconomic?: number;
    };

    rawMetrics: Record<string, MetricValue>;

    uncertainties: string[];

    verificationRequired: string[];

    sources: MetricSource[];
};

type MetricValue = {
    value: number | string | null;
    unit?: string;
    status:
        | "observed"
        | "calculated"
        | "scenario"
        | "proxy"
        | "unknown";
};

Do not spread arbitrary backend JSON throughout React components.

Validate incoming API data.

If the project already uses a schema-validation library, use it.

Otherwise choose a lightweight TypeScript-compatible validation
approach.

Invalid records should fail gracefully rather than crash the map.
